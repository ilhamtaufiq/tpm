# TPM — Aturan Bisnis & Invariant Finansial

⬅️ [[CLAUDE|Kembali ke Hub]]

## ⚖️ Invariant Finansial (Critical — jangan dilanggar)

1. **Anti Rp0**: dilarang membuat jurnal kas/bank/piutang dengan nominal Rp0.
2. **Prinsip Double-Entry**: setiap mutasi kas masuk/keluar harus punya akun lawan seimbang. Total Aktiva (Aset/Kas/Piutang) = Total Pasiva (Kewajiban/Hutang + Modal + Laba Ditahan).
3. **Immutability Jurnal**: transaksi berjurnal **tidak boleh** `DELETE` fisik dari database. Kesalahan input/pembatalan wajib pakai **Reversal Transaction** (jurnal balik) untuk menihilkan efek nominal.
4. **Integrasi Kasir Mandiri (User Cash)**: setiap transaksi kasir wajib terikat sesi kas aktif (`user_cash`). Kasir tidak bisa bertransaksi sebelum buka kas awal, dan wajib rekonsiliasi (tutup kas) di akhir shift.

## 📊 Invariant Laporan & Import Saldo Awal

1. **Modal Awal = Aktiva − Hutang pada tanggal saldo awal** (anchor = tanggal impor `IMP-*` paling awal), dihitung sekali lalu beku di `system_settings.modal_awal_frozen`. Angka manual Rp2.242.611.225 hanya berlaku untuk anchor **2026-09-12**; import periode berikutnya selalu memakai nilai hitung.
2. **Filter non-impor wajib null-safe**: `nomor_referensi IS NULL OR nomor_referensi NOT LIKE 'IMP-%'`. `NOT LIKE` saja membuang baris ber-`nomor_referensi` NULL (mis. setoran modal manual).
3. **Setoran, prive, dan laba di Perubahan Modal = periode filter** (sama dengan Laba Rugi). Sisa kumulatif sejak anchor s/d sehari sebelum `tanggal_dari` tampil di *Laba Ditahan Sebelumnya* dan *Setoran Modal / Prive Bersih Sebelumnya* (`mutasi_modal_sebelumnya`), agar Modal Awal + mutasi = Modal Akhir.
4. **Baris "Penyesuaian Transaksi Backdate"** = penyeimbang transaksi non-impor bertanggal **sebelum** tanggal saldo awal (tidak tercakup Modal Awal beku maupun arus periode). Nilai bertanda (+ di Penambahan, − di Pengurangan) dan disertai daftar transaksinya (`backdate_detail`). Tanpa transaksi semacam itu nilainya harus 0 — selain itu audit.
5. **Import mobil mengisi `harga_beli_awal = harga_beli`.** Selisih keduanya = revaluasi stok (setoran non-kas); tanpa ini seluruh harga opening terbaca revaluasi.
6. **Persentase bagi hasil investor diisi manual per mobil setelah import** (template tidak punya kolom ini; default 0% = seluruh laba ke TPM).
7. **Koreksi data berbasis ID produksi tidak boleh jalan otomatis tanpa cek nama** — setelah reset + import ulang, ID menunjuk record lain. `heal_sparepart_stock_discrepancies` kini cek nama + sekali jalan (flag `heal_sparepart_stock_20260928_done`).
8. **Cek silang `/laporan/validate`**: laba Laba Rugi (`laba_operasional`, sebelum prive) dibandingkan dengan `info.laba_operasional` Perubahan Modal — bukan `laba_bersih` yang sudah dipotong prive.
9. **Guard anti-duplikat KasBank** (ber-`nomor_referensi`): kunci = jenis + tipe + nomor_referensi + referensi_id + tanggal + **nominal + keterangan**. DP lalu pelunasan mobil / cicilan di hari yang sama sah; hanya input ulang identik yang ditolak 409.
10. **`/validate` cek hutang**: hutang snapshot modal dikurangi `piutang_booking` dulu (Neraca menetting piutang booking ke piutang), agar booking DP tidak memunculkan MISMATCH palsu.
11. **Pembelian aset tetap** (Master Data → Aset → Pembelian Aset Tetap, seperti pembelian spare part) wajib memilih sumber dana: *Tunai Utama / Transfer* (Kas Keluar sumber `ASET`, bisa split; sisa yang belum dibayar jadi hutang ke supplier/penjual, `nomor_referensi` = kode aset), *Hutang Penuh*, atau *Setoran Pemilik* (setoran modal non-kas di Perubahan Modal). Hutang aset **bukan beban** Laba Rugi. Hapus aset = kas dibalik `[VOID]` + hutang belum dibayar ikut dihapus; ditolak bila hutangnya sudah dicicil. Aset tanpa `sumber_dana` (klien lama / import) tetap hanya terdaftar.
12. **Edit transaksi bengkel internal** (JB Mobil / Jasa Angkut) wajib menyamakan piutang & hutang internal ke `grand_total` baru (`_sync_internal_debts_nominal`); baris yang sudah LUNAS tetap lunas di nominal baru.
13. **Tes backend tidak boleh mematok angka/ID data produksi.** Tes laporan memakai saldo awal aktif s/d hari ini dan memeriksa invariant (balance, Modal Awal beku, kas = Σ mutasi, menu stok = Neraca). Wajib lulus di DB kosong, setelah import xlsx, dan setelah transaksi.
14. **Edit harga beli / stok spare part di Master Data wajib berjejak** (`_catat_penyesuaian_persediaan`): harga beli berubah (stok > 0) → `SparePartRevaluation` senilai (harga baru − harga lama) × stok lama; stok berubah → `SparePartRevaluation(is_qty_correction=True)` senilai Δqty × harga beli, tampil sebagai Koreksi Stok Opname (bukan Penyesuaian Backdate).
15. **Nilai persediaan historis** (Neraca tanggal lampau) = stok×harga sekarang − pembelian sesudah tanggal + pemakaian sesudah tanggal − **revaluasi & koreksi qty sesudah tanggal**. Tanpa dua suku terakhir persediaan lampau menggelembung dan Modal Awal beku ikut salah.
16. **Edit tanggal transaksi bengkel** memindahkan baris keuangan yang lahir bersamanya (kas pembayaran, piutang, pembayaran, hutang internal yang bertanggal sama dengan tanggal lama); cicilan belakangan tetap di tanggal aslinya.
17. **Harga jual di nota boleh diubah** (override harga master): pendapatan = harga nota. HPP memakai harga beli terakhir, sama dengan nilai persediaan, jadi penjualan tidak memunculkan selisih harga lagi.
18. **Persediaan spare part dinilai harga beli terbaru (stok × harga beli)**, sama persis dengan daftar stok. Selisih harga stok lama saat harga beli berubah (pembelian dengan harga baru atau edit Master Data) **langsung** diakui di *Penyesuaian Harga Beli Spare Part* (positif = laba, negatif = rugi) di Perubahan Modal dan bagian Modal Neraca — tidak menunggu terjual, bukan baris Laba Rugi. *Koreksi Stok Opname* = Σ Δqty × harga beli. Keduanya ikut dijumlah di Perubahan Bersih Modal (app, PDF, dashboard) sehingga Modal Awal + aliran = Modal Akhir.
19. **Tanggal transaksi tidak boleh melewati hari ini (WIB).** Schema input (piutang, hutang, pembayaran, pengeluaran, pembelian part, nota bengkel, muatan, kasbon, mobil, aset) menolak 422 dan `KasBankService.create` menolak 400 (ikut transfer & penyesuaian saldo). Kas bertanggal besok tidak terhitung di Neraca/Kas hari ini → saldo sistem diam-diam beda dengan real. Frontend wajib memakai tanggal lokal `getTodayString()`, **bukan** `toISOString()` (UTC, mundur sehari sebelum 07:00 WIB). Baris lama dikoreksi dengan `backend/scripts/fix_tanggal_masa_depan.py`.
20. **Tidak ada lagi revaluasi "belum terealisasi".** Tabel `spare_part_revaluation_release` masih terisi saat penjualan tetapi tidak dipakai laporan (sejak 6 Okt 2026).
21. **Setoran modal sebelum saldo awal tetap terlihat sebagai Penambahan Modal.** Setoran MODAL non-impor bertanggal < anchor sudah ada di Modal Awal beku (snapshot Neraca anchor). Porsinya dikeluarkan dari Modal Awal tampilan (`modal_awal − setoran_pra_anchor`) dan diakui sebagai setoran: jatuh di periode filter → *Penambahan Modal*, sisanya → *Setoran Modal Bersih Sebelumnya*. Modal Akhir tidak berubah. Setoran MODAL tidak didaftar lagi di `backdate_detail`. Catatan: setoran pra-anchor yang dibuat *setelah* Modal Awal beku diambil tetap jatuh ke Penyesuaian Backdate (tidak dipotong dari Modal Awal).
22. **Refund DP pembatalan booking JB Mobil** punya dua mode. `HUTANG` (default): sisa DP jadi hutang `UANG_MUKA_PENJUALAN`, kas tidak berubah, dilunasi dari menu Hutang. `LANGSUNG`: kas KELUAR per baris metode/kas pilihan, total baris wajib = sisa DP (DP − penalti), tanpa hutang baru. Refund langsung + penalti = DP terbayar. Pembatalan penjualan LUNAS (`cancel-sale`) punya mode yang sama: `LANGSUNG` membalik seluruh uang masuk pembeli dari kas pilihan; `HUTANG` tidak menyentuh kas dan mencatat sisa uang diterima (masuk − keluar) sebagai hutang `UANG_MUKA_PENJUALAN`.
23. **Hutang gaji karyawan (akrual absensi).** Absensi HADIR / SETENGAH_HARI bertanggal ≥ **12 Okt 2026** diakui saat diisi: Dr Beban Gaji / Cr Hutang Gaji (`gaji_akrual_service`). Nilai harian = gaji_pokok / 6 × faktor (1 / 0.5), dibulatkan per baris. Slip periode ≥ cutoff memakai gaji_pokok = jumlah akrual absensi periode itu, dan jumlah hadir tidak boleh di-override. Saat slip cair, gaji_pokok mengurangi hutang gaji (bukan beban lagi); kas dan kasbon seperti biasa; lembur tetap beban saat cair. Absensi yang tanggalnya sudah tercakup slip (apa pun statusnya) tidak bisa diubah atau dihapus; hapus slip yang belum cair dulu. Slip periode akrual hanya dibuat setelah periodenya selesai (tanggal akhir ≤ hari ini WIB), supaya absensi hari berjalan tidak terkunci. Periode sebelum cutoff tidak berubah. Nomor minggu slip adalah minggu ISO (Senin–Sabtu), sama dengan `get_current_week` dan UI; `get_week_dates` mengikutinya (sebelumnya memakai skema "Senin pertama tahun", sehingga slip mingguan menghitung absensi di minggu yang salah dan gajinya 0). Slip per karyawan hanya satu per minggu ISO (unique constraint) dan rentang tanggal slip tidak boleh tumpang tindih. Slip yang dilewati saat generate dilaporkan dengan alasannya, dan karyawan yang sudah punya slip di rentang itu tidak muncul lagi sebagai pending. Dashboard (ringkasan & harian) menampilkan pengeluaran gaji = beban gaji (gaji pokok akrual + slip lama + lembur), sama dengan Laba Rugi, bukan gaji bersih yang dicairkan.
24. **`KasBank.referensi_id` tidak unik antar sumber.** Kas muatan memakai `referensi_id = muatan.id` + `nomor_referensi = nomor_transaksi muatan`; kas pembayaran piutang memakai `referensi_id = pembayaran.id` + `nomor_referensi = nomor piutang`. Setiap lookup/update/void kas wajib memasangkan `referensi_id` dengan `nomor_referensi` (atau keterangan yang memuat nomor transaksi). Bug 13 Okt 2026: edit muatan menjadi LUNAS mencari kas hanya dengan `referensi_id == muatan.id`, menimpa 3 kas pembayaran piutang 8 Okt (KAS2610080014/15/17: 1.200.000 TRANSFER, 1.100.000 TRANSFER, 750.000 TUNAI) menjadi nilai laba_tpm muatan lain dan memindahkannya ke Kas Unit Jasa Angkut. Diperbaiki di `muatan_service` (reconcile LUNAS, sinkron tanggal, void) + test `test_muatan_kas_collision.py`. Aturan terkait: (a) edit muatan yang piutangnya sudah LUNAS tidak boleh membuat kas "Pemasukan Jasa Angkut" lagi — uangnya sudah tercatat lewat kas pembayaran piutang (dulu JAS2610130014 tercatat ganda 495.000 di Kas Unit JA, lalu ikut disetor 1.620.000 ke bank sebagai saldo semu); (b) bila harga muatan yang sudah lunas via piutang dinaikkan, piutang dibuka lagi sebesar selisih bagian TPM (status SEBAGIAN, muatan BELUM_LUNAS) dan ditagih lewat pembayaran piutang; bila bagian TPM turun di bawah yang sudah dibayar, edit ditolak. (c) Void transaksi bengkel menghapus kas miliknya hanya bila `nomor_referensi` = nomor transaksi / nomor piutangnya; dulu filter `referensi_id == transaksi.id` ikut menghapus kas pembayaran piutang lain (13 Okt 2026 16:52: void BGL2610130004 id 31 menghapus kas pembayaran #31 PTG2610050006 "RETUR KIT TURBO" 350.000 TUNAI, Kas Utama). Test `test_bengkel_void_kas_collision.py`. Audit semua lookup kas berbasis `referensi_id` yang menulis/menghapus (14 Okt 2026): kasbon delete, edit pembelian part, reversal pencairan investor, dan void pembayaran piutang muatan kini juga mensyaratkan `nomor_referensi`. Sisa satu join read-only (breakdown per armada di ringkasan JA). Rekap selisih yang dilaporkan user (neraca 2.000.000): Kas Utama 1.100.000 = 750.000 (KAS2610080017 tertimpa) + 350.000 (kas retur terhapus); Bank 900.000 = 2.300.000 (KAS2610080014/15 tertimpa) − 1.620.000 (setoran semu) + 220.000 (selisih harga JAS2610130007/14). Koreksi data produksi: `backend/scripts/fix_kas_tertimpa_muatan.py` (mode kering default, `--apply` hanya ID eksplisit); diuji di salinan dump 13 Okt → Penyesuaian Backdate −2.007.000 menjadi −7.000 (sisa drift Modal Awal).
25. **Retur pembelian spare part ke supplier** (`retur_pembelian_service`, tabel `retur_pembelian_spare_parts`). Nilai retur R = Σ qty × harga_satuan baris pembelian. Efek: (a) stok part berkurang qty (tidak untuk stok always-ready); (b) hutang pembelian yang masih terbuka dikurangi dulu sebesar min(R, sisa hutang) — nominal dan sisa hutang turun bersama, total_dibayar tetap; (c) sisa R setelah hutang dipotong (seluruh R bila pembelian sudah lunas) diakui sebagai salah satu: **kas/bank** — kas MASUK sumber PEMBELIAN_PART dengan metode refund yang dipilih (`nomor_referensi` = nomor retur, bukan nomor pembelian), atau **piutang ke supplier** — PiutangUsaha sumber LAINNYA (`referensi_id` = retur, `nomor_referensi` = nomor retur) yang dilunasi lewat menu Piutang seperti piutang biasa. Pembatalan retur dengan piutang yang sudah dibayar ditolak. (d) bila hutang menjadi lunas karena retur, status pembelian ikut LUNAS dengan tanggal bayar = tanggal retur, sehingga `update_payment` tidak mencatat kas lagi. Persediaan dinilai stok × harga_beli terbaru, jadi retur **hanya diizinkan** bila harga_beli part masih sama dengan harga_satuan baris (selisih nilai persediaan tidak boleh muncul). Qty retur per baris ≤ sisa yang belum diretur dan ≤ stok sekarang. Pembelian yang punya retur aktif tidak bisa diedit atau dihapus. Pembatalan retur (void) membalik stok, hutang, dan kas (entri [VOID]); retur tidak dihapus. Laporan (Neraca, Perubahan Modal, validasi) tetap seimbang: diuji di salinan dump produksi, retur tunai dan retur kredit tidak mengubah Penyesuaian Backdate. Catatan: laporan pembelian (grand_total per nota) belum dikurangi retur; nilai bersih retur tersedia di daftar retur per pembelian.
26. **Hak akses fitur unit (bengkel, mobil, jasa angkut).** Role unit hanya membuka fitur miliknya, plus ADMIN dan MANAGER: BENGKEL mencatat pembayaran transaksi bengkel (`PATCH /transaksi-bengkel/{id}/payment`); MOBIL mencatat penjualan mobil, pembayarannya, biaya, dan part service (`/penjualan-mobil`, `/mobil/{id}/biaya`, `/mobil/{id}/part-service`) serta ringkasannya; JASA_ANGKUT mengedit dan membatalkan muatan (`PUT` dan `POST /muatan/{id}/void`) serta ringkasannya. Pembatalan penjualan, pencairan investor, hapus transaksi/muatan, dan biaya muatan tetap ManagerUser. Dependency per role: `require_roles` di `app/api/deps.py`. Logika keuangan (jurnal, saldo, hutang/piutang) tidak berubah; yang berubah hanya siapa yang boleh memanggilnya. Dicakup oleh `test_role_access_unit.py`.
27. **Pembayaran hutang hanya TUNAI atau TRANSFER; keterangan kas memuat metodenya.** `PembayaranHutangCreate` dan `PembayaranHutangSplit` memakai `PaymentDetailHutang` (schema di `keuangan.py`), sehingga KREDIT, SPLIT, dan INTERNAL ditolak 422 sebelum menyentuh kas. Sesuai PaymentModal yang hanya menawarkan Tunai dan Transfer untuk hutang. Keterangan kas KELUAR: pembayaran hutang `Pembayaran hutang {nomor} - {kreditur} ({metode})` (`hutang_service`); pelunasan dari pembelian part `Pelunasan hutang {nomor} (Pembelian Part: {nomor_transaksi}) ({metode})` dan tanpa hutang `Pelunasan pembelian spare part - {nomor_transaksi} ({metode})` (`pembelian_part_service.update_payment`). Routing akun tetap dari `get_kas_jenis(metode)`, jadi keterangan hanya penanda, bukan penentu saldo. Catatan: metode pelunasan pembelian part belum dibatasi ke Tunai/Transfer.
28. **Piutang manual wajib punya metode pencairan (TUNAI atau TRANSFER) atau split payment.** `PiutangCreate` menolak input tanpa keduanya (validator di `keuangan.py`), dan opsi "Tidak Ada" di form piutang dihapus. Piutang tanpa kas keluar tidak punya lawan di kas. Neraca menghitung Modal sebagai Aktiva − Hutang, jadi aset tanpa lawan diam-diam masuk Modal dan `is_balanced` selalu lolos. Piutang lama yang dibuat tanpa metode tetap ada dan belum dikoreksi. Piutang dari transaksi unit, muatan, dan retur tidak lewat jalur ini.
29. **Tanggal "hari ini" dan tampilan tanggal mengikuti WIB (server), bukan zona mesin.** Deploy Docker menetapkan `TZ=Asia/Jakarta`, jadi `date.today()` di server sudah WIB. Backend tetap memakai `get_jakarta_date()` / `get_jakarta_now()` supaya tidak bergantung pada env. Penyebab tanggal tampil mundur 1 hari ada di frontend: `new Date('YYYY-MM-DD')` dibaca sebagai UTC midnight, lalu di perangkat dengan zona di belakang WIB tampil hari sebelumnya. Aturan: tanggal saja dari server diubah dengan `tanggalLokal()` (utils/format.ts) atau `formatDate()` sebelum ditampilkan. `getTodayString()` tanpa argumen memakai WIB. Test yang mem-patch "hari ini" harus mem-patch `app.utils.helpers.get_jakarta_date` juga, karena validator masa depan memakainya. Jam perangkat diselaraskan dengan jam server lewat `GET /system/server-time` (selisih dihitung saat app dibuka dan tiap 10 menit, `services/serverTime.ts`); `getTodayString()` memakai selisih itu.
30. **Halaman Perbaikan Data di dashboard web (folder `dashboard`, route `/perbaikan`, hanya ADMIN/MANAGER lewat `/perbaikan-data`).** Aplikasi mobile tidak punya layar ini. Dua temuan dengan aksi koreksi: (a) piutang manual tanpa kas (LAINNYA, tanpa referensi, tanpa baris kas bernomor sama): catat kas keluar pada tanggal piutang. Akun bisa dipilih: TUNAI ke Kas Utama atau laci unit (Bengkel, Jasa Angkut, Jual Beli Mobil); TRANSFER hanya ke Bank Utama (akun lain ditolak 400), atau batalkan (status BATAL, sisa 0) bila memang tidak ada uang keluar; (b) baris kas yang tanggalnya 1 hari sebelum tanggal input (`DATEDIFF(created_at, tanggal) = 1`, IMP-* dikecualikan): pindahkan tanggal semua baris kas bernomor sama dan induknya (piutang, hutang, transaksi bengkel) lalu hitung ulang saldo. Tanggal baru tidak boleh melewati hari ini (WIB). Setiap aksi dicatat di tabel `perbaikan_data_log` (jenis, nomor, nilai sebelum dan sesudah, pengguna) dan ditampilkan sebagai Riwayat perbaikan di halaman Perbaikan Data. Riwayat tidak bisa diubah dari halaman. Koreksi ini tidak menyentuh pembayaran piutang/hutang dan dokumen selain tiga induk di atas.

## 📝 Aturan Pengembangan (Dev Guidelines)

1. **Business Logic Isolation**: dilarang keras query DB, manipulasi model finansial, atau kalkulasi harga langsung di route controller (`api/v1/endpoints/`). Wajib dibungkus di service class (`app/services/`).
2. **Schema Validation**: semua data masuk dari frontend wajib divalidasi Pydantic v2 (`app/schemas/`) sebelum diproses ORM.
3. **Database Changes**: semua perubahan kolom/tabel/index wajib lewat migrasi Alembic baru:
   ```bash
   alembic revision --autogenerate -m "deskripsi_perubahan"
   alembic upgrade head
   ```
4. **Immutability Pattern (Frontend Store)**: dilarang mutasi state Zustand langsung — gunakan dispatcher yang mengembalikan salinan state baru (immutable), sesuai `coding-style.md`.
5. **Code-first Models**: SQLAlchemy 2.x `Mapped`/`mapped_column`. Semua skema di `app/models/` — enum baru wajib ditambahkan ke `app/utils/constants.py` agar tercakup migrasi autogenerate.
